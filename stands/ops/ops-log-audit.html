Журналирование, auditd и ротация логов

journald, auditd, logrotate и разбор инцидента по таймлайну событий.

формат: индивидуально · разбор инцидента примерно 5 ч начисление: 85 неткоинов

О работе

спринт 4 · Эксплуатация · 5 ч · 85 неткоинов

systemd-journald, auditd, logrotate и поиск инцидента в логах без воды и паники.

Бриф практики

выдра Лина — аудитор журналов · бриф практики

После ночного инцидента с правами доступа выяснилось, что логи никто не читает, а часть журналов вообще не пережила перезагрузку. Вы наведёте порядок в журналировании сервисов ДатаПолиса: настроите постоянное хранение journald, правила auditd на критичные файлы, ротацию через logrotate и отработаете разбор реального инцидента по таймлайну событий.

Теория

опорный конспект

01 journald: уровни, фильтры и персистентность

journalctl умеет фильтровать по юниту, приоритету, времени и идентификатору. По умолчанию журнал может жить в tmpfs и пропадать после ребута; Storage=persistent в journald.conf создаёт /var/log/journal.

# journalctl -u sshd --since 'today 09:00' --until '09:30'
# journalctl -p err -b
# journalctl -f
# mkdir -p /var/log/journal && systemctl restart systemd-journald

02 auditd: правила наблюдения за критичными файлами

auditd пишет события доступа к объектам, а не только сообщения сервисов. Правило -w ставит наблюдение за файлом, -p rwxa — какие операции, -k задаёт метку для быстрого поиска через ausearch.

# apt-get install audit
# systemctl enable --now auditd
# auditctl -w /etc/sudoers -p wa -k sudoers-change
# auditctl -w /etc/ssh/sshd_config -p wa -k sshd-hardening
# ausearch -k sudoers-change
# aureport --summary -i

03 logrotate: размер, сроки и сжатие

Ротация не даёт логам съесть диск: daily/weekly, rotate N поколений, compress, delaycompress для файлов, которые дописываются. После правки конфига обязательна проверка logrotate -d (dry-run).

/var/log/app/*.log {
  daily
  rotate 14
  compress
  missingok
  notifempty
  create 0640 app app
  postrotate
    systemctl kill -s HUP app.service
  endscript
}
# logrotate -d /etc/logrotate.d/app

⚑ Диск, забитый логами, — частая причина аварии: ротация относится к эксплуатации, а не к «уборке потом».

Бэклог задач

чек-лист
  1. Включите постоянное хранение journald, перезагрузите сервис и подтвердите каталог /var/log/journal
  2. Соберите таймлайн событий sshd за учебное окно: успешные входы, неуспешные попытки, время и источники
  3. Установите auditd и добавьте наблюдение за /etc/sudoers и /etc/ssh/sshd_config с метками
  4. Смоделируйте правку sudoers и найдите событие через ausearch по метке, разберите поля записи
  5. Напишите конфиг logrotate для учебного приложения: дневная ротация, 14 поколений, сжатие, postrotate HUP
  6. Прогоните logrotate -d и исправьте все предупреждения до рабочего прогона
  7. На Windows сопоставьте события Security (4624/4625) с журналами Linux: оформите таблицу соответствия источников
  8. Напишите runbook дежурного «первые 5 команд при разборе инцидента» и проведите самооценку по чек-листу

Задача считается выполненной после реальной работы на оборудовании, в эмуляторе или на виртуальной машине. В интерактиве чек-лист сохраняет прогресс.

Заявка

P3

Навести порядок в журналировании сервисов

тип: incident · приоритет: P3

Ночная смена не смогла восстановить таймлайн доступа: журналы частично пропали после перезагрузки, аудит прав sudoers не включён, диск одного из серверов на 92% занят старыми логами. Привести журналирование к управляемому виду и подготовить runbook разбора инцидента.

Runbook

Разбор инцидента по журналам

  1. Зафиксировать время обнаружения и окно инцидента
  2. Снять журналы затронутых юнитов через journalctl с фильтром времени
  3. Проверить auditd/security-канал на изменения конфигов и входы
  4. Собрать таймлайн: причина, первое событие, распространение, восстановление
  5. Оформить запись в базе знаний и предложить правило/алерт на повторение

Проверь себя

контрольный тест
Вопрос 1. Почему журнал journald может пропасть после перезагрузки?
  • Так задумано для безопасности
  • Хранение в tmpfs без Storage=persistent верно
  • journalctl удаляет старое при ребуте
  • Нужен платный модуль

Ответ: Хранение в tmpfs без Storage=persistent

Без persistent-режима журнал живёт в /run/log/journal (tmpfs) и очищается вместе с памятью.

Вопрос 2. Что делает правило auditd -w /etc/sudoers -p wa -k sudoers-change?
  • Блокирует файл на запись
  • Наблюдает за записью и изменением атрибутов файла и помечает события меткой верно
  • Ежедневно делает бэкап
  • Шифрует sudoers

Ответ: Наблюдает за записью и изменением атрибутов файла и помечает события меткой

-w — наблюдение, -p wa — write/attribute, -k — метка для поиска через ausearch -k.

Вопрос 3. Зачем запускать logrotate -d перед боевым прогоном?
  • Это удаляет старые логи
  • Dry-run показывает, что ротация сделает, без реальных изменений верно
  • Он сжимает диск
  • Так включается сервис

Ответ: Dry-run показывает, что ротация сделает, без реальных изменений

-d — режим отладки: видны ошибки путей и правок, ничего не ротируется по-настоящему.

Вопрос 4. Какой код события Windows соответствует успешному входу?
  • 4625
  • 4688
  • 4624 верно
  • 1102

Ответ: 4624

4624 — успешный логон, 4625 — неудачный, 4688 — создан процесс, 1102 — очистка журнала аудита.

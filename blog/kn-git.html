Git в работе администратора: ветка, откат, конфиг

Git нужен администратору не для красоты, а чтобы отвечать на вопрос «что изменилось и когда» — в конфигурации, в плейбуке, в скрипте. Три команды (status, diff, log) дают больше, чем час воспоминаний, а revert безопаснее reset.

Конфигурация сервера, лежащая в Git, отвечает на вопрос «кто и когда это сломал» за секунды. Конфигурация, лежащая в голове и в /etc, отвечает на него в лучшем случае через час. Это не про модность инструмента, а про то, что история изменений — часть инфраструктуры.

Три области, а не одна

Git хранит изменения в трёх местах: рабочее дерево (ваши файлы), индекс (то, что попадёт в следующий коммит) и репозиторий (уже сохранённые коммиты). Понимание этой схемы объясняет всё остальное: git add переносит из дерева в индекс, git commit — из индекса в репозиторий, git diff --staged показывает разницу между индексом и последним коммитом.

git add -p — самая недооценённая команда: она позволяет принять изменения по кускам, а не файлом целиком. Это и есть способ делать осмысленные коммиты, когда в одном файле смешаны две правки.

Ветка — это указатель

Ветка в Git — не копия каталога, а имя, указывающее на коммит. Создание ветки мгновенно, переключение почти мгновенно, и это меняет подход: любую правку можно делать отдельно, не боясь сломать рабочее состояние.

git switch -c fix/nginx-timeout
# ... правки ...
git commit -am "nginx: увеличить proxy_read_timeout для отчётов"
git switch main
git merge --no-ff fix/nginx-timeout

Откат: revert, а не reset

git revert создаёт новый коммит, который отменяет изменения указанного. История остаётся линейной и честной, и это безопасно, если репозиторий уже разошёлся по другим машинам. git reset --hard переписывает историю и стирает незакоммиченные изменения — допустимо только локально и только когда вы точно знаете, что делаете.

Если нужно вернуть один файл к состоянию из коммита: git checkout <sha> -- path/to/file (в новых версиях — git restore --source=<sha> path). Это точечная операция, которая не трогает остальное.

Конфликт — это не поломка

Конфликт возникает, когда две ветки изменили одни и те же строки. Git не может выбрать за вас и оставляет маркеры:

<<<<<<< HEAD
proxy_read_timeout 60s;
=======
proxy_read_timeout 300s;
>>>>>>> fix/nginx-timeout

Правка простая: оставить нужный вариант, удалить маркеры, git add файл, git commit. Важное правило — не «разрешать конфликт», а понимать, какой вариант правильный: второй раз эта строка может конфликтовать больнее.

Конфигурация, которая экономит время

git config --global user.name "Имя"
git config --global init.defaultBranch main
git config --global pull.rebase true
git config --global core.pager "less -FRX"
git config --global alias.lg "log --oneline --graph --decorate -20"

pull.rebase true избавляет от лишних merge-коммитов при работе в одиночку. core.pager не оставляет пустой экран при коротком выводе. Алиас lg — компактная история, которую видно с первого взгляда.

Что хранить в репозитории

Конфигурации сервисов, плейбуки, скрипты, документацию, схемы — да. Секреты, пароли, приватные ключи, дампы баз — нет, никогда. Даже в приватном репозитории секрет остаётся в истории, и «удалить коммитом» его не убирает: нужен git filter-repo и смена самого секрета.

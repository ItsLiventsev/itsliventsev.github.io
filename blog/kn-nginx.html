nginx как reverse proxy: что важно кроме proxy_pass

Директива proxy_pass — это три строки, а рабочая конфигурация — это заголовки, таймауты, буферы и логи. Именно они определяют, будет ли прокси быстрым, честным в логах и предсказуемым при отказе бэкенда.

Машинная обработка. Текст структурирован и оптимизирован с помощью ИИ: структура, формулировки и визуальные блоки собраны ассистентом, источники и наблюдения — авторские. Даты обращения к источникам указаны.

nginx ставят как «прокси перед приложением», и на этом останавливаются. Через месяц выясняется, что в логах приложения все клиенты — это адрес прокси, загрузка файлов падает с 413, а при медленной базе пользователи получают 504 через минуту. Всё это свойства конфигурации, а не приложения.

Клиент виден только через заголовки

Приложение за прокси видит адрес nginx. Чтобы оно знало настоящий адрес клиента, прокси передаёт его заголовком:

location / {
    proxy_pass http://app_backend;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Connection "";
}

Риск здесь очевидный: X-Forwarded-For — обычный заголовок, его подставит кто угодно, если nginx слушает мир напрямую. Поэтому приложение должно доверять заголовку только от известного прокси, а nginx — перезаписывать его, а не добавлять к пользовательскому. Для этого есть модуль real_ip с явным списком доверенных сетей.

proxy_http_version
1.1 — без этого нет keepalive к бэкенду
Connection
пустое значение вместе с 1.1 включает переиспользование
proxy_read_timeout
60 с по умолчанию; длинные отчёты требуют большего
client_max_body_size
1 МБ по умолчанию — тихая причина 413

Таймауты: где живёт «минута»

proxy_connect_timeout — сколько ждать установки соединения; 60 секунд по умолчанию, разумно снизить до 3–5. proxy_read_timeout — сколько ждать данных от бэкенда между чтениями. Если приложение обрабатывает тяжёлый отчёт две минуты и не отдаёт ничего, а таймаут 60 — пользователь получит 504, хотя запрос ещё выполняется. Обратная ошибка тоже бывает: таймаут 600 секунд на публичном API означает, что зависшие запросы копятся и съедают воркеры.

Буферы, тела и keepalive

client_max_body_size — самая частая причина «загрузка не работает, а в приложении ошибок нет». Поднимайте его в конкретном location, а не глобально.

proxy_buffering on позволяет nginx принять ответ целиком и отдать клиенту в его темпе: хорошо для медленных клиентов, плохо для SSE — там буферизацию отключают, иначе события приходят пачками.

По умолчанию nginx ходит в бэкенд по HTTP/1.0 и закрывает соединение после каждого запроса. На нагрузке это тысячи лишних рукопожатий. Лечится группой с keepalive 32 и парой директив из таблицы выше. Это одна из самых дешёвых оптимизаций: пропадает установка соединения, и задержка ответа падает.

Проверка и наблюдаемость

Логи — первое. Формат с $request_time, $upstream_response_time и $upstream_addr сразу показывает, кто тормозил: разница между двумя первыми числами и есть время, потерянное вне приложения. nginx -T проверяет конфигурацию целиком, stub_status или экспортёр дают метрики для мониторинга.

Про сертификаты, без которых прокси бесполезен снаружи, — TLS и сертификаты; про то, кто может молча отбросить соединение до nginx, — файрвол.

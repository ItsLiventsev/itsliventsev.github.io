Ansible: плейбук, который можно запускать дважды

Плейбук описывает желаемое состояние, а не последовательность команд; идемпотентный модуль на повторном запуске показывает changed=0, и это главный признак того, что автоматизация написана правильно.

Машинная обработка. Текст структурирован и оптимизирован с помощью ИИ: структура, формулировки и визуальные блоки собраны ассистентом, источники и наблюдения — авторские. Даты обращения к источникам указаны.

Ansible выиграл не потому, что он самый мощный, а потому что не требует агента: подключается по SSH (см. настройку sshd) и работает поверх обычного Python. Но именно эта простота провоцирует писать плейбуки как скрипты — с shell на каждом шаге, без проверки состояния и без возможности запустить второй раз.

Идемпотентность на пальцах

Идемпотентный плейбук при повторном запуске не меняет ничего. Это не стилистическое требование, а практическое: без него нельзя ни перезапустить упавшую задачу, ни применить конфигурацию к уже настроенному хосту.

- hosts: web
  become: true
  tasks:
    - name: nginx установлен
      ansible.builtin.apt:
        name: nginx
        state: present

    - name: конфиг из шаблона
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        validate: "nginx -t -c %s"
      notify: reload nginx

    - name: служба включена
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded

Три вещи здесь важны:

  1. template пишет файл только если содержимое отличается — отсюда changed=0 при повторном запуске.
  2. validate проверяет конфиг до подмены: синтаксическая ошибка не уронит работающий сервис.
  3. notify + handler перезагружает nginx один раз, даже если его изменили несколько задач, и только если что-то изменилось.

Почему shell ломает всё

- ansible.builtin.shell: systemctl restart nginx

Такой шаг всегда changed, всегда выполняется и ничего не знает о состоянии системы. Замена — модуль service, который сначала проверит, а потом сделает. Если модуля нет, добавляют creates/removes или changed_when, чтобы задача стала проверяемой.

--check и --diff

ansible-playbook site.yml --limit web --check --diff

--check прогоняет плейбук без изменений и показывает, что было бы сделано. --diff печатает различия в файлах. Это единственный безопасный способ применить изменения к чужому продакшену: сначала посмотреть отчёт, потом запускать по-настоящему.

Ограничение: задачи, которые зависят от предыдущих (например, проверка только что установленного пакета), в check-режиме могут врать. Поэтому в отчёт смотрят, а не верят ему слепо.

Инвентарь и переменные

[web]
web1.example.org
web2.example.org

[db]
db1.example.org

Хост не должен «знать, кто он»: роль определяется группой, параметры — group_vars/web.yml. Тогда один и тот же плейбук применяется к тестовой и продуктивной среде без правок.

Секреты не хранят в открытом виде: ansible-vault шифрует файл переменных, пароль передаётся отдельно.

Что должно быть в репозитории

  • site.yml — точка входа, роли подключаются списком.
  • roles/<имя>/tasks|templates|handlers — по одной роли на компонент.
  • inventory/ и group_vars/ — окружения.
  • README с порядком применения и откатом.

И главное: плейбук в git — это документация инфраструктуры. Если сервер настроен руками и в репозитории этого нет, сервер восстанавливается только по памяти. О том, как ещё и бэкапить состояние — 3-2-1, о том, как проверять службы после деплоя — systemd и мониторинг.

ЗадачаМодульЧто делает при повторе
поставить пакетansible.builtin.aptничегоесли уже стоит
положить конфигansible.builtin.templateпишет только при отличии
запустить службуansible.builtin.serviceвключает и стартует один раз
создать пользователяansible.builtin.userне меняет существующего
выполнить командуansible.builtin.commandвсегда выполняется
Если задача меняет систему, для неё почти всегда есть модуль — и он умеет проверять текущее состояние.

Связанные заметки

3 связи
  • SSH: ключ вместо пароля и что закрыть в sshded25519 и passphrase, что именно проверять перед закрытием пароля, fail2ban как следствие, а не решение, и sftp без доступа к shell.
  • systemd: юниты, цели и порядок загрузкиunit, target и wants, enable против start, override через systemctl edit и три команды, которые отвечают почти на любой вопрос о службе.
  • Prometheus: четыре типа метрик и один хороший алертrate и histogram_quantile, почему CPU > 80% — плохой алерт, что такое for: 5m и как не утонуть в уведомлениях.

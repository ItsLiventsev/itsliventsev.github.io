Файрвол в Linux: nftables и порядок правил

Файрвол — это список правил, который читается сверху вниз и останавливается на первом совпадении. Поэтому половина «файрвол не пускает» — это правило, стоящее выше нужного, а половина «файрвол не защищает» — отсутствие политики по умолчанию.

Машинная обработка. Текст структурирован и оптимизирован с помощью ИИ: структура, формулировки и визуальные блоки собраны ассистентом, источники и наблюдения — авторские. Даты обращения к источникам указаны.

Файрвол в Linux — это не программа, а набор точек в сетевом стеке, где можно посмотреть на пакет и решить его судьбу. Точки называются хуками, а правила — цепочками. Понимание этой схемы снимает 90 % путаницы: люди ищут «где блокируется», не зная, что пакет может пройти через три разных хука и в каждом встретить свой вердикт.

Пять хуков

Пакет, пришедший на интерфейс, сначала попадает в prerouting — здесь ещё не известно, предназначен он этому хосту или будет перенаправлен. Дальше маршрутизация разводит его: себе — в input, дальше — в forward. Исходящий от процессов идёт через output, а покидающий хост — через postrouting.

{huki}

Практический вывод: правило для транзитного трафика бесполезно писать в input, а DNAT — в postrouting. Ошибка «правило есть, но не работает» почти всегда означает не тот хук.

Порядок важнее содержания

Правила читаются сверху вниз, и первое совпадение выносит вердикт. Значит, accept для доверенной сети должен стоять до общего drop, а не после — иначе он не сработает никогда. В nftables это ещё и решается наличием политики цепочки: policy drop означает «что не разрешено явно, то запрещено», и это единственный способ писать файрвол, который действительно защищает.

nft list ruleset
nft add table inet filter
nft add chain inet filter input '{ type filter hook input priority 0; policy drop; }'
nft add rule inet filter input ct state established,related accept
nft add rule inet filter input iif lo accept
nft add rule inet filter input tcp dport 22 accept

Conntrack: почему не нужен ответный порт

Состояния соединений ведутся отдельно от правил. Разрешив ct state established,related, вы автоматически разрешаете ответные пакеты, не открывая при этом входящие порты. Это и есть причина, по которой не нужно (и вредно) писать парные правила «туда и обратно».

{sostoyanija}

INVALID — отдельная строка: такие пакеты обычно отбрасывают с логом, потому что они означают либо асимметричную маршрутизацию, либо мусор от сканера. Если после настройки «ничего не работает», начните с conntrack -S и посмотрите, не растёт ли insert_failed — это верный признак того, что таблица переполнена и новые соединения молча отбрасываются.

Три способа открыть лишнее

  1. -A INPUT -j ACCEPT в конце. Одна такая строка отменяет всю предыдущую работу: политика больше не применяется.
  2. Открытый порт на все интерфейсы. tcp dport 5432 accept пускает базу откуда угодно. Нужно iif eth0 ip saddr 10.20.30.0/24 tcp dport 5432 accept.
  3. Правило без счётчика и без проверки. Правило, которое «вроде есть», может не совпадать по интерфейсу или семейству адресов. iptables -L -n -v показывает счётчики пакетов — именно они говорят, сработало правило или нет.

Как проверять

Сначала — nft list ruleset или iptables-save и глазами: политика, порядок, интерфейсы. Потом — счётчики: у каждого правила видно, сколько пакетов оно пропустило. Если счётчик нулевой, правило не совпадает; если растёт на правиле drop, вы нашли, что блокирует.

Дальше — tcpdump на нужном интерфейсе: видно, доходит ли SYN и есть ли SYN-ACK. Это разделяет две разные проблемы — «пакет не дошёл» и «пакет дошёл, но ответ не прошёл». Подробнее в заметке про tcpdump и в разборе TCP: если SYN уходит, а SYN-ACK не возвращается, файрвол — первый подозреваемый.

## Путь запроса

Клиент (браузер, приложение) обращается к stub-резолверу в системе, тот — к рекурсивному резолверу (обычно у провайдера или корпоративный). Рекурсивный резолвер, если ответа нет в кеше, идёт по цепочке:

1. **Корневые серверы** (`.`) отвечают: «за зону `.com` отвечают вот эти адреса».
2. **Серверы зоны `.com`** отвечают: «за `example.com` — вот эти NS».
3. **Авторитетные серверы зоны** отвечают нужной записью: `A 203.0.113.10`.

Резолвер кеширует ответ на время TTL. Именно поэтому смена A-записи доходит неравномерно: у кого-то TTL истёк и адрес новый, у кого-то кеш живёт ещё сутки.

## Типы записей

| Тип | Отвечает на вопрос | Пример |
| --- | --- | --- |
| A / AAAA | какой адрес у имени | `192.0.2.10`, `2001:db8::10` |
| CNAME | это псевдоним | `www → example.com` |
| MX | куда отдавать почту | `10 mail.example.com` |
| TXT | произвольные данные | SPF, DKIM, подтверждения |
| NS | кто отвечает за зону | `ns1.example.com` |
| SRV | служба и порт | `_sip._tcp` |

CNAME нельзя ставить на вершину зоны (`example.com`), потому что там обязаны быть NS и SOA. Эта ошибка встречается чаще остальных при переносе сайта.

## Настройка зоны

Минимальный файл зоны для BIND:

```conf
$TTL 3600
@   IN SOA ns1.example.local. admin.example.local. (
        2026110401 ; serial — менять при каждой правке
        3600       ; refresh
        900        ; retry
        1209600    ; expire
        300 )      ; negative TTL
@   IN NS  ns1.example.local.
ns1 IN A   192.168.10.10
www IN A   192.168.10.20
mail IN A  192.168.10.25
@   IN MX  10 mail.example.local.
ftp IN CNAME www
```

Serial — единственное поле, про которое забывают. Если он не изменился, вторичный сервер не увидит правку и будет отдавать старые данные.

Проверка конфигурации перед перезапуском:

```bash
named-checkzone example.local /etc/bind/db.example.local
rndc reload
```

## Резолвинг на клиенте

```bash
dig www.example.com              # полный ответ с секциями
dig +short www.example.com       # только адрес
dig @192.168.10.10 www.example.com   # спросить конкретный сервер
dig +trace www.example.com       # пройти всю цепочку самому
resolvectl status                # какой резолвер реально используется
```

`dig +trace` — лучший инструмент, когда «не работает у всех»: он показывает, на каком шаге цепочка обрывается. Если обрыв на авторитетных серверах, проблема в зоне; если на корневых — в сети или фильтрации.

Типичные коды ответа:

| Код | Значение | Что это значит |
| --- | --- | --- |
| NOERROR | ответ есть | смотрите секцию ANSWER |
| NXDOMAIN | имени не существует | опечатка или запись не создана |
| SERVFAIL | сервер не смог | ошибка зоны или недоступность авторитетного |
| REFUSED | отказано | ACL на сервере |

## Внутренние и внешние зоны

Рабочая схема организации: внутренняя зона (например, `example.local`) обслуживается корпоративным DNS и не видна из интернета; внешняя зона (`example.com`) живёт у регистратора или у провайдера. Смешивать их в одном сервере можно, но нужно следить, чтобы внутренние имена не утекали наружу — иначе карта сети становится доступной.

## Итог

- Запрос идёт: клиент → рекурсивный резолвер → корень → зона → авторитетный сервер.
- TTL определяет, как долго живёт кеш, и объясняет «неравномерную» смену адреса.
- Serial в SOA — причина, по которой вторичный сервер не видит изменений.
- `dig +trace` показывает точку обрыва; коды ответа сужают причину.

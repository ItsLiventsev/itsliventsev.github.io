## Условие

Киберспортивная арена: 20 игровых мест в зале, тренерская на 2 места, администраторская стойка, зона ожидания с Wi-Fi. Турниры проводятся внутри зала, связь с интернетом нужна для обновлений и стрима, но матчи идут по локальному серверу.

Ключевое требование — **стабильная задержка**. Пропускная способность у игрового трафика смешная (килобиты на игрока), а вот скачок с 8 до 80 мс портит матч.

## Почему задержка, а не скорость

| Метрика | Игровой трафик | Что ломает |
| --- | --- | --- |
| Пропускная способность | 50–200 Кбит/с на игрока | почти ничего |
| Задержка | до 30 мс до игрового сервера | прицеливание, реакция |
| Джиттер | до 5 мс | «телепорты» персонажей |
| Потери | до 0,5 % | рассинхрон, откаты |

Отсюда решения: приоритет игровому трафику в очереди, отдельный VLAN, никакого Wi-Fi на игровых ПК, ограничение обновлений и стрима по полосе.

## Зоны и адресация

| Сегмент | Подсеть | Примечание |
| --- | --- | --- |
| Игровые ПК | 10.40.10.0/24 | статические адреса, приоритет в очереди |
| Турнирный сервер | 10.40.15.0/28 | доступен только из игрового и тренерского сегментов |
| Тренерская и админ | 10.40.20.0/28 | доступ к управлению оборудованием |
| Гости | 10.40.30.0/24 | Wi-Fi, изоляция клиентов, ограничение скорости |
| Управление | 10.40.250.0/24 | только из админской |

Игровые адреса статические: DHCP-аренда, истёкшая посреди матча, — реальная причина «вылетов», которую долго ищут.

## Оборудование

- Коммутатор доступа на 24 порта с поддержкой QoS и VLAN (игровые места).
- Магистраль до ядра — два агрегированных канала (LACP), чтобы обрыв одного кабеля не останавливал турнир.
- Ядро — маршрутизатор с очередями и приоритизацией.
- Wi-Fi — отдельная точка доступа на гостевую зону, не пересекающаяся по каналам с оборудованием зала.

## Настройка приоритета

```conf
# игровой трафик — в приоритетную очередь
nft add table inet qos
nft add chain inet qos out '{ type filter hook postrouting priority 0; }'
nft add rule inet qos out ip saddr 10.40.10.0/24 ip dscp set cs4
```

```text
# на коммутаторе: очередь с приоритетом для портов игрового сегмента
qos priority-queue 4
interface range gigabitEthernet 0/1-24
  qos trust dscp
```

Приоритет без ограничения сверху — ловушка: гостевое обновление Windows забирает канал целиком. Поэтому на гостевой и служебный сегмент ставится лимит полосы.

## Проверка, которая имеет смысл

```bash
# задержка и джиттер до игрового сервера
ping -c 50 10.40.15.10
# потери на длинном интервале
ping -i 0.2 -c 500 10.40.15.10 | tail -3
# ошибки на порту
ethtool -S eth0 | grep -i err
```

Проверять надо **на всех 20 местах**, а не на одном: порт с дефектом коннектора даёт потери только у одного игрока, и это выглядит как «у него руки кривые».

## Сценарий турнира

1. За час до начала — проверка всех мест скриптом: пинг, потери, скорость линка.
2. Обновления Windows и игры — только до турнира, после начала служба обновлений отключается.
3. Стрим — с отдельного ПК, полоса ограничена, чтобы не конкурировать с игрой.
4. Во время матча — мониторинг задержки и потерь, а не «на глаз».
5. После — журнал: какие места дали отклонения.

## Типичные провалы

- **Wi-Fi для игроков.** Джиттер в разы выше, никакой QoS не спасает.
- **DHCP на игровых местах.** Аренда истекает в самый неподходящий момент.
- **Один кабель до ядра.** Обрыв — и турнир остановлен.
- **Нет лимита на обновления.** Один ноутбук забирает канал у всех.
- **Проверка «в целом».** Дефект одного порта находят уже во время матча.

## Итог

- Проектировать надо под задержку и джиттер, а не под гигабиты.
- Игровой сегмент отдельный, статический, с приоритетом и без Wi-Fi.
- Магистраль резервируется агрегацией каналов.
- Проверка идёт по каждому месту, а не по одному.

## Порядок решает всё

Фильтр обрабатывает правила сверху вниз и останавливается на первом совпадении. Поэтому «разрешить всё, запретить конкретное» и «запретить конкретное, разрешить всё» — разные политики, хотя выглядят похоже.

```text
# так запрет никогда не сработает
permit any any
deny  tcp 10.0.0.5 eq 23

# так — сработает
deny  tcp 10.0.0.5 eq 23
permit any any
```

Второе правило из этой логики: у списка должно быть действие по умолчанию, и оно должно быть явным. Неявное «разрешить всё» — самая распространённая ошибка в учебных работах.

## Что именно фильтровать

| Что | Зачем | Пример |
| --- | --- | --- |
| Входящие соединения | оставить только нужные порты | 22 с адресов администраторов, 80/443 всем |
| Исходящие | не дать увести данные | блок необычных портов наружу |
| Транзит между зонами | изоляция отделов | запрет гостям в серверный сегмент |
| Служебные протоколы | защита самого устройства | не пускать к маршрутизатору из интернета |

Отдельно про **обратный трафик**: фильтр состояний (conntrack) позволяет отвечать на разрешённые соединения автоматически. Без него приходится разрешать и входящие, и исходящие порты, что почти всегда ошибка.

## nftables: рабочий шаблон

```bash
nft list ruleset > /root/nft-backup.txt   # сначала сохранить текущее состояние
```

```conf
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    ct state established,related accept
    iif "lo" accept
    ip protocol icmp accept
    tcp dport 22 ip saddr 192.168.10.0/24 accept
    tcp dport { 80, 443 } accept
    counter drop
  }
  chain forward {
    type filter hook forward priority 0; policy drop;
  }
  chain output {
    type filter hook output priority 0; policy accept;
  }
}
```

Разбор по строкам:

- `policy drop` — по умолчанию запрещено. Всё, что не разрешено явно, не проходит.
- `ct state established,related` — ответный трафик разрешён, это обязательная первая строка.
- `iif "lo" accept` — петлевой интерфейс, без него ломаются локальные службы.
- `counter drop` — счётчик отброшенного: по нему видно, что именно блокируется.

## Проверка без блокировки себя

Классическая ситуация: применили правило и потеряли SSH. Порядок безопасной работы:

1. Открыть второй сеанс SSH и держать его.
2. Применить правила.
3. Проверить новый вход в третьем сеансе.
4. Только потом закрыть старые.

```bash
nft -c -f rules.nft        # проверка синтаксиса без применения
nft -f rules.nft           # применение
nft list ruleset           # что реально загружено
nft monitor trace          # трассировка (на новых версиях)
```

Дополнительно полезно поставить откат по таймеру:

```bash
echo 'nft flush ruleset' | at now + 5 minutes
```

Если что-то пошло не так, правила исчезнут сами, и доступ вернётся.

## Частые ошибки

- **Нет правила для established.** Соединения устанавливаются, но ответы блокируются — «сайт открывается через раз».
- **Порядок: permit any выше deny.** Запрет не работает.
- **Блокировка ICMP.** Ломается Path MTU Discovery: ping идёт, а скачивание зависает. См. [[kn-mtu]].
- **Фильтр на входе, но не на транзите.** Гости попадают в серверный сегмент напрямую.
- **Правила не сохраняются после перезагрузки.** Проверять `systemctl status nftables` и конфигурацию автозагрузки.

## Итог

- Первое совпадение побеждает: порядок важнее содержания.
- Действие по умолчанию должно быть явным и, как правило, `drop`.
- conntrack обязателен, ICMP не блокируют.
- Проверка — через второй сеанс, с откатом по таймеру.

## Задача, которую решает VLAN

В одном опенспейсе сидят бухгалтерия, отдел разработки и гости. Им нужен общий коммутатор, но не нужен общий широковещательный домен: гостевой ноутбук не должен видеть служебный трафик, а разработка не должна ловить широковещательные штормы бухгалтерии.

VLAN решает это логически: порты одного коммутатора группируются в виртуальные сети, и кадр из VLAN 10 физически не может попасть в VLAN 20. Коммутатор ведёт для каждого VLAN отдельную таблицу MAC-адресов, то есть внутри одного устройства работают как бы несколько независимых коммутаторов.

Номер VLAN — 12 бит в теге, значит допустимы значения 1–4094. VLAN 1 обычно остаётся служебным, и держать на нём пользователей не стоит: это удобная мишень и лишний широковещательный домен.

## Access и trunk

| Тип порта | Что происходит с кадром | Куда подключают |
| --- | --- | --- |
| Access | кадр принимается и отдаётся без тега, порт закреплён за одним VLAN | компьютер, принтер, камера |
| Trunk | кадры всех разрешённых VLAN идут с тегом 802.1Q | коммутатор — коммутатор, коммутатор — маршрутизатор |
| Hybrid | и тегированные, и нетегированные VLAN | встречается на части оборудования |

Тег 802.1Q — 4 байта: 2 байта TPID (`0x8100`) и 2 байта управления, где 12 бит — номер VLAN и 3 бита — приоритет (PCP). Именно эти 4 байта уменьшают полезную нагрузку кадра, и именно поэтому при расчёте MTU транка их учитывают.

Порт, к которому подключён компьютер, обязан быть access: если оставить trunk, компьютер получит тегированные кадры, которые не поймёт, — линк поднимется, обмена данными не будет.

## Настройка на коммутаторе

```text
vlan 10
 name office
vlan 20
 name guests
interface gi0/1
 switchport mode access
 switchport access vlan 10
interface gi0/24
 switchport mode trunk
 switchport trunk allowed vlan 10,20
```

Две строки в транке важнее остальных: `allowed vlan` ограничивает список, а `native vlan` задаёт VLAN для нетегированных кадров. Правило безопасности: нативный VLAN на транке меняют с 1 на любой неиспользуемый, иначе появляется способ протащить трафик «без тега» в служебный домен.

## Проверка после настройки

```text
show vlan brief                  — какие порты в каких VLAN
show interfaces trunk            — какие транки подняты и какие VLAN разрешены
show interfaces switchport       — режим и VLAN конкретного порта
```

В Linux VLAN навешивается на интерфейс:

```bash
ip link add link eth0 name eth0.10 type vlan id 10
ip link set eth0.10 up
ip -d link show eth0.10
```

## Межвлановый обмен

VLAN изолирует — значит, чтобы отделы общались, нужен маршрутизатор. Есть два способа:

1. **Router-on-a-stick.** Один физический интерфейс в транке, на нём подынтерфейсы по VLAN.
   ```text
   interface gi0/0.10
    encapsulation dot1Q 10
    ip address 192.168.10.1 255.255.255.0
   ```
2. **SVI на L3-коммутаторе.** Виртуальный интерфейс на каждый VLAN, включённый `ip routing`.
   ```text
   interface vlan 10
    ip address 192.168.10.1 255.255.255.0
   ip routing
   ```

Второй способ быстрее и привычнее в современных сетях, первый остаётся в учебных задачах и на старом оборудовании.

## Частые ошибки

- **Транк вместо access на рабочем месте.** Линк есть, данных нет.
- **VLAN не разрешён в транке.** Пинг через коммутатор не идёт, хотя локально всё работает.
- **Разные VLAN на концах.** Один порт в VLAN 10, второй в 20 — кадры уходят «в никуда».
- **Нативный VLAN не совпадает.** Часть кадров уходит без тега и попадает в служебный домен.
- **Шлюз не настроен.** VLAN работают, но между собой не общаются, потому что нет SVI или подынтерфейса.

## Итог

- VLAN — это логическое деление коммутатора на домены, а не «настройка порта».
- Access отдаёт кадр без тега, trunk переносит теги 802.1Q по списку разрешённых.
- Связь между VLAN обеспечивает маршрутизатор или L3-коммутатор.
- Три проверки после настройки: `show vlan brief`, `show interfaces trunk`, пинг между VLAN.

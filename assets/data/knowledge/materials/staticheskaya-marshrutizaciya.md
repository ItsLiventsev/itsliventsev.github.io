## Как маршрутизатор выбирает

Маршрутизатор не «ищет лучший путь» в бытовом смысле. Он ищет самое длинное совпадение: из всех маршрутов, покрывающих адрес назначения, выбирается тот, у которого больше длина префикса. Если совпадений с одинаковой длиной несколько — решает административная дистанция (метрика источника), затем метрика протокола.

Пример таблицы на маршрутизаторе филиала:

```text
S    0.0.0.0/0 [1/0] via 203.0.113.1
S    10.20.0.0/16 [1/0] via 192.168.10.1
C    192.168.10.0/24 is directly connected, gi0/0
L    192.168.10.2/32 is directly connected, gi0/0
```

Буквы означают источник: `C` — подключён напрямую, `L` — локальный адрес интерфейса, `S` — статический маршрут. Пакет на `10.20.5.5` попадёт в маршрут /16, а не в `0.0.0.0/0`: /16 длиннее.

## Маршрут по умолчанию

`0.0.0.0/0` — «всё, что не описано точнее, отправить сюда». Это запись, без которой сеть не выходит в интернет:

```text
ip route 0.0.0.0 0.0.0.0 203.0.113.1
```

Или через интерфейс (работает не на всех платформах, но встречается в учебных стендах):

```text
ip route 0.0.0.0 0.0.0.0 gi0/1
```

Разница важна: маршрут через next-hop требует доступности соседа по ARP, маршрут через интерфейс — нет, но плохо работает на многоточечных средах вроде Ethernet, где за одним интерфейсом много соседей.

## Статика на Linux

```bash
ip route add 10.20.0.0/16 via 192.168.10.1
ip route add 0.0.0.0/0 via 203.0.113.1
ip route show
ip route get 8.8.8.8
```

Записи `ip route add` живут до перезагрузки. Чтобы маршрут сохранялся, его вносят в конфигурацию сети (NetworkManager, systemd-networkd, `/etc/network/interfaces` — в зависимости от дистрибутива).

## Резервный маршрут

Два канала в интернет — основной и резервный. Оба маршрута по умолчанию существуют одновременно, но выбирается один: с меньшей метрикой (или административной дистанцией).

```text
ip route 0.0.0.0 0.0.0.0 203.0.113.1          ! основной, AD 1
ip route 0.0.0.0 0.0.0.0 198.51.100.1 250     ! резерв, AD 250
```

Пока основной интерфейс в состоянии up, работает первый маршрут. Как только он пропадает, второй становится активным. Дефект очевиден: если канал «поднят», но не работает, переключения не будет — для этого нужны либо IP SLA, либо динамический протокол.

На Linux резерв делают метрикой:

```bash
ip route add 0.0.0.0/0 via 203.0.113.1 metric 100
ip route add 0.0.0.0/0 via 198.51.100.1 metric 200
```

## Ошибки, которые встречаются чаще всего

- **Шлюз недоступен напрямую.** Маршрут есть, но следующий хоп не в той подсети, что интерфейс. `ip route get` покажет проблему.
- **Маска маршрута шире реальной.** `10.0.0.0/8` через филиал забирает весь трафик, включая локальные подсети.
- **Маршрут без обратного пути.** Пакет уходит, ответ не возвращается — классика при настройке статики между двумя маршрутизаторами.
- **Дубли маршрутов в разных источниках.** Статика и динамика на один префикс: побеждает меньшая дистанция, и не всегда это то, что ожидали.

## Проверка

```text
show ip route                     — таблица на оборудовании
show ip route 10.20.5.5           — какой маршрут выберется
traceroute 10.20.5.5              — фактический путь
```

```bash
ip route get 10.20.5.5            — какой маршрут выберет ядро Linux
traceroute -n 10.20.5.5
```

`ip route get` — самый недооценённый инструмент: он отвечает не «какие маршруты есть», а «куда именно уйдёт этот пакет». В сложных таблицах это единственный быстрый способ проверить политику.

## Итог

- Побеждает самый длинный совпадающий префикс, затем административная дистанция.
- `0.0.0.0/0` — маршрут по умолчанию, без него нет выхода наружу.
- Резервный маршрут делается метрикой и не спасает, если канал «поднят, но мёртв».
- `ip route get` показывает реальный выбор, а не список маршрутов.

Контейнер не эмулирует железо: он запускает обычный процесс, которому ядро показывает урезанную картину мира. `namespaces` отвечают за то, что процесс видит (свои PID, сеть, точки монтирования), `cgroups` — за то, сколько ресурсов он может взять. Понимание этой пары объясняет и быстрый старт, и то, почему контейнер не заменяет виртуальную машину там, где нужна жёсткая изоляция.

## Образ собирается слоями

Каждая инструкция в Dockerfile добавляет слой, и слои кешируются. Отсюда правило: **сначала то, что меняется редко**. Скопировать список зависимостей и установить их — потом копировать исходники. Если сделать наоборот, любая правка в коде сбрасывает кеш установки, и сборка занимает минуты вместо секунд.

```dockerfile
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

FROM python:3.12-slim
WORKDIR /app
COPY --from=build /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY --from=build /app /app
USER 10001
CMD ["python", "-m", "app"]
```

Multi-stage сборка — способ не тащить в прод компиляторы и заголовочные файлы. Итоговый образ получается в разы меньше, а поверхность атаки — уже.

## Данные, сеть, конфигурация

1. **Данные.** Файл, записанный внутри контейнера, исчезнет при пересоздании. База должна писать в том или в каталог хоста. Том управляется Docker и переживает контейнер; bind mount — просто путь на хосте, удобен для конфигов, но зависит от прав и SELinux.
2. **Сеть.** Контейнеры одной пользовательской сети видят друг друга по имени сервиса. Порт, опубликованный через `-p`, доступен снаружи — и обычно нужен только для отладки.
3. **Конфигурация.** Не вшивайте секреты в образ: они останутся в слоях навсегда. Переменные окружения при запуске, файлы — через секреты или монтирование.

## Диагностика

Контейнер упал — смотрите не `docker ps`, а `docker logs` и `docker inspect --format '{{.State.ExitCode}}'`. Код 137 — это SIGKILL, чаще всего OOM: приложение съело лимит памяти. Код 1 — приложение само завершилось с ошибкой, читайте его вывод. Пустой лог при падении почти всегда означает, что приложение писало в файл внутри контейнера.

Для отладки сети удобен отдельный контейнер в сети проблемного: `docker run --rm -it --network container:<id> nicolaka/netshoot`. В минимальных образах нет ни `ps`, ни `curl`, и это нормально.

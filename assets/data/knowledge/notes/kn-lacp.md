Соблазн понятен: два гигабитных кабеля — значит два гигабита. На практике это верно только для суммы. Каждый отдельный поток — одна TCP-сессия, один бэкап, одна копия файла — выбирает **один** физический линк по хешу, и этот поток быстрее гигабита не поедет. Отсюда типичное разочарование: «сделали агрегацию, а scp всё равно 110 МБ/с».

## Что делает LACP

LACP — это протокол согласования: обе стороны обмениваются LACPDU и подтверждают, что видят друг друга в одной группе. Без согласования легко получить ситуацию, когда коммутатор считает линки независимыми и половина трафика уходит в никуда, а при двух кабелях между одним и тем же оборудованием — петля и шторм.

Режимы: **active** инициативно шлёт LACPDU, **passive** ждёт. Две passive-стороны между собой не договорятся никогда — это частая причина «агрегация не поднялась» при формально правильной настройке.

## Хеш важнее ширины

Коммутатор считает хеш от полей пакета: обычно пара MAC, пара IP и иногда порты. Все пакеты одного потока получают одинаковое значение и уходят в один линк. Значит, выигрыш зависит от количества потоков: сотня клиентов за прокси распределится хорошо, а один rsync с одним соединением не распределится вовсе.

Отсюда практическое правило: агрегацию делают ради **резервирования и суммарной полосы для многих потоков**, а не ради ускорения одного. Если нужен быстрый одиночный поток — это 10G, а не четыре по 1G. И если хеш считается только по MAC, а весь трафик идёт через один шлюз, все потоки получат один и тот же линк: настройка хеша по IP и портам здесь не роскошь.

## Настройка в Linux

```bash
ip link add bond0 type bond mode 802.3ad miimon 100 lacp_rate fast
ip link set eth1 master bond0
ip link set eth2 master bond0
cat /proc/net/bonding/bond0     # состояние, активные порты, партнёр
```

`miimon 100` — проверка линка раз в 100 мс. Без неё отказ кабеля замечается только по таймауту LACP, и это десятки секунд тишины. `lacp_rate fast` ускоряет обмен до секунды — полезно на время ввода в эксплуатацию, потом можно вернуть slow: лишние кадры каждую секунду на сотнях портов никому не нужны.

## Диагностика по шагам

1. **Смотрим локально:** `cat /proc/net/bonding/bond0` — все ли порты в состоянии up и виден ли партнёр. Пустой partner означает, что LACPDU не доходят.
2. **Смотрим на коммутаторе:** `show etherchannel summary` — флаги `P` (в группе), `U` (используется), `s` (подвешен). Порт в `s` — чаще всего не совпали настройки или режим.
3. **Сверяем параметры:** скорость, дуплекс, MTU, список VLAN. Один порт в группе с другим MTU ломает всю группу, а не только себя.
4. **Проверяем раскладку:** несколько параллельных `iperf3 -P 4` покажут сумму, одиночный `iperf3` — потолок одного линка. Разница между этими двумя числами и есть ответ на вопрос «работает ли агрегация».

Что важно не забыть: агрегация не отменяет STP. Если кабели воткнуты в разные коммутаторы, нужен либо стек, либо MSTP с правильными приоритетами, иначе часть портов будет заблокирована и ожидаемого выигрыша не будет. Об этом — [[kn-stp|заметка про STP]]; про тегирование в агрегированном канале — [[kn-vlan|802.1Q]].

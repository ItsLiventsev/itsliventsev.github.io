Имя удобно людям, адрес — машинам, а DNS — это распределённая база соответствий между ними. У неё нет единой копии: зоны живут на разных серверах, а между клиентом и авторитетным сервером стоит кэширующий резолвер, который и делает всю работу.

## Путь одного запроса

Клиентская программа вызывает stub-резолвер, тот отправляет один UDP-пакет на адрес из `/etc/resolv.conf` (или из DHCP). Дальше начинается рекурсия:

1. **Резолвер** смотрит свой кэш. Если запись там есть и TTL не истёк — отвечает сразу, без сети.
2. Если нет — спрашивает корневой сервер: «кто отвечает за `.ru`?». Получает адреса серверов зоны.
3. Спрашивает сервер зоны `.ru`: «кто отвечает за `example.ru`?».
4. Спрашивает авторитетный сервер зоны и получает конкретную запись.
5. Кладёт ответ в кэш на время TTL и возвращает клиенту.

Каждый шаг — отдельный короткий обмен. Типичное время «холодного» запроса — десятки миллисекунд, повторного из кэша — единицы.

## TTL — это про задержку изменений

TTL — количество секунд, которое ответ можно кэшировать. Пока запись в кэше, изменения на авторитетном сервере никто не увидит. Отсюда практическое правило: перед плановой сменой адреса уменьшите TTL за сутки (например, до 300 секунд), подождите, пока старый TTL истечёт, смените запись, а через сутки верните прежнее значение.

То же касается отрицательных ответов: NXDOMAIN тоже кэшируется, и «я исправил зону, а ошибка осталась» — это TTL у отрицательного ответа.

## Два резолвера — две правды

В корпоративной сети часто есть локальный резолвер (с внутренними зонами) и внешний. Клиент отправляет запрос одному из них, и если внутренняя зона есть только у локального, а клиент спросил внешний — он получит NXDOMAIN.

Отсюда два инструмента:

- **split-DNS** — разные ответы для внутренних и внешних клиентов; обязательный атрибут любой организации с внутренними сервисами.
- **условная пересылка** — резолвер отправляет запросы на домен организации локальному серверу, остальное — наружу.

Проверить, кто отвечает, можно явно:

```bash
dig @192.0.2.53 example.ru A +short     # спросить конкретный сервер
dig example.ru +trace                    # пройти всю цепочку от корня
resolvectl status                        # какие резолверы реально используются
```

## UDP 53, TCP 53 и 512 байт

Классический DNS работает по UDP на порт 53. Ответ ограничен 512 байтами, если стороны не договорились об ином. Расширение EDNS(0) (RFC 6891) позволяет передавать больший размер через поле OPT в дополнительной секции. Когда ответ не влезает, сервер ставит флаг TC (truncated), и клиент повторяет запрос по TCP.

Практический вывод: не блокируйте TCP 53 «потому что DNS — это UDP». DNSSEC-ответы и большие наборы записей ходят именно по TCP.

## Что проверять первым

1. `resolvectl status` или `cat /etc/resolv.conf` — какой сервер настроен.
2. `dig @<сервер> имя` — отвечает ли сам сервер.
3. `dig имя` — работает ли путь через системный резолвер.
4. `dig +trace имя` — где именно обрывается цепочка.
5. `tcpdump -ni any port 53` — уходит ли запрос и приходит ли ответ.

Если запросы уходят, а ответов нет — почти всегда файрвол на пути или адрес резолвера совпадает с адресом, который сам раздаётся по [[kn-dhcp|DHCP]] с ошибкой. И наоборот: «интернет есть, а сайты не открываются по имени» — это классика DNS, а не канала.

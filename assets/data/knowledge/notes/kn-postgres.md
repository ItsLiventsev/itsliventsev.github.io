PostgreSQL выбрал стратегию MVCC: читатель не блокирует писателя, потому что писатель не меняет существующую строку, а создаёт новую версию. Читатель видит ту версию, которая была актуальна в момент начала его запроса. Это даёт отличную конкурентность и создаёт необходимость в обслуживании.

## Что происходит при UPDATE

1. Транзакция получает номер XID.
2. В старой версии строки записывается `xmax = этот XID` — «эта версия больше не актуальна».
3. Рядом появляется новая версия с `xmin = этот XID`.
4. После COMMIT новые транзакции видят новую версию, а старые — старую.

Старая версия физически остаётся на диске. Она не видна никому, но занимает место. Это и есть мёртвый кортеж.

## VACUUM: почему не «очистить и сжать»

`VACUUM` помечает место мёртвых версий как свободное для повторного использования. Таблица при этом не становится меньше на диске: файл остаётся того же размера, но внутри появляются свободные страницы. `VACUUM FULL` переписывает таблицу целиком и возвращает место файловой системе, но блокирует таблицу на всё время работы — на большой базе это часы простоя.

Отсюда практика: `autovacuum` включён всегда, а `VACUUM FULL` — только осознанно и по необходимости.

```sql
-- сколько мёртвых строк и когда последний раз чистили
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
```

## Заворот счётчика XID

Номер транзакции — 32 бита, и сравнение «что новее» работает только в пределах 2^31 транзакций. Когда счётчик подходит к границе, старые версии будут выглядеть как «будущие» и станут невидимыми — то есть данные пропадут.

Защита — `freeze`: VACUUM помечает очень старые версии специальным признаком «видима всегда», и их больше не надо сравнивать. Автоматически это запускается, когда возраст самой старой незамороженной транзакции превышает `autovacuum_freeze_max_age` (по умолчанию 200 миллионов).

Если freeze не успевает (например, autovacuum заблокирован долгой транзакцией, которая держит горизонт видимости), база приближается к пределу и при 2^31−1 уходит в режим только для чтения с сообщением про wraparound. Это не «упало»: это защита от порчи данных.

```sql
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
```

Значение больше 1,5 миллиарда — повод разбираться немедленно. Причина почти всегда одна: кто-то открыл транзакцию и забыл закрыть (`idle in transaction`).

## Что настроить, чтобы этого не было

1. `idle_in_transaction_session_timeout` — рвёт сессии, которые держат транзакцию открытой без работы.
2. Мониторинг `age(datfrozenxid)` с алертом на 1 млрд.
3. `autovacuum_vacuum_scale_factor` поменьше для больших таблиц: 20% от миллиона строк — это двести тысяч мёртвых кортежей до первой уборки.
4. Не отключать autovacuum «для производительности»: он вернётся в виде аварии.
